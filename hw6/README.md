# Домашнее задание: база данных и AJAX

В этом задании проект начинает хранить данные в реляционной БД (MariaDB), а часть страниц
переходит на AJAX: данные загружаются и отправляются без перезагрузки страницы.

База данных разворачивается **локально** на вашем компьютере одной командой через Docker.

## Подготовка: локальная БД


1. Установите [Docker Desktop](https://www.docker.com/products/docker-desktop/)
   (Windows: при установке включите WSL 2; macOS: подходит и Intel, и Apple Silicon).
2. В корне проекта выполните:

   ```bash
   docker compose up -d
   ```

   Поднимутся два контейнера:
   - **MariaDB** на `localhost:3306`, база `wp`, пользователь `wp`, пароль `wp`;
   - **Adminer** — веб-интерфейс к БД на <http://localhost:8081>
     (System: `MySQL / MariaDB`, Server: `db`, Username: `wp`, Password: `wp`, Database: `wp`).

   При самом первом запуске (пока база пустая) автоматически выполняется `sql/schema.sql` —
   таблица `User` уже будет создана.
3. Параметры подключения уже прописаны в `profile.properties`:

   ```properties
   database.url=jdbc:mariadb://localhost:3306/wp?useUnicode=true&characterEncoding=UTF-8
   database.user=wp
   database.password=wp
   ```

Пример схемы — `sql/schema.sql` в исходном виде:

```sql
CREATE TABLE `User` (
    `id`           BIGINT       NOT NULL AUTO_INCREMENT,
    `login`        VARCHAR(255) NOT NULL,
    `passwordSha`  VARCHAR(255) NOT NULL,
    `creationTime` DATETIME     NOT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_User_login` (`login`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

Полезные команды:

| Что сделать | Команда |
|---|---|
| Запустить БД | `docker compose up -d` |
| Остановить БД (данные сохранятся) | `docker compose stop` |
| Применить SQL-файл к базе | `docker compose exec -T db mariadb -uwp -pwp wp < файл.sql` |
| Консоль MariaDB | `docker compose exec db mariadb -uwp -pwp wp` |
| Логи БД | `docker compose logs db` |


### Данные сохраняются — не удаляйте их

База хранится в томе Docker (`db-data`) на вашем компьютере. Всё, что вы зарегистрировали и создали,
**сохраняется** после:

- `docker compose stop` и повторного `docker compose up -d`;
- закрытия Docker Desktop, IDE или перезагрузки ноутбука;
- `docker compose down` (контейнеры удаляются, том с данными остаётся).

**Задание сдаётся на вашем ноутбуке с вашими данными.** К сдаче в базе должны быть пользователи
(в том числе администратор), статьи (в том числе скрытые), сообщения и события входа/выхода, накопленные
за время работы над заданием. Поэтому **не удаляйте том `db-data`** (например, в Docker Desktop → Volumes) — восстановить данные
будет нельзя.

### Как менять схему БД

`sql/schema.sql` выполняется автоматически **только один раз** — при создании пустой базы.
Поэтому изменения структуры вносите так:

1. Выполните SQL на своей базе — через Adminer (<http://localhost:8081> → «SQL-запрос»)
   или консоль `docker compose exec db mariadb -uwp -pwp wp`. Например:

   ```sql
   ALTER TABLE `User` ADD COLUMN `email` VARCHAR(255) NULL;
   ```
2. **Тот же самый SQL допишите в конец `sql/schema.sql`.** Этот файл — полная история схемы
   вашего проекта: выполненный по порядку на пустой базе, он должен давать ровно ту структуру,
   которая сейчас у вас в БД. Его проверяют при сдаче.

## Запуск проекта

Нужны JDK 11+ и Maven (в IntelliJ IDEA Maven встроен).

**Самый простой способ** — встроенный Jetty:

```bash
mvn jetty:run
```

Сайт откроется на <http://localhost:8080>. Шаблоны `.ftlh`, css и js подхватываются без перезапуска,
после изменения Java-кода перезапустите команду.
В IntelliJ IDEA то же самое: панель Maven → Plugins → jetty → `jetty:run`.

**Через Tomcat** (если привыкли): нужен **Tomcat 9** — проект использует `javax.servlet`,
на Tomcat 10+ он не запустится. В IDEA: Run → Edit Configurations → Tomcat Server → Local,
Deployment → artifact `wp-db-ajax:war exploded`, Application context `/`.

Проверьте, что всё работает: зарегистрируйтесь, войдите, и в Adminer в таблице `User` появилась запись.

### Если что-то не работает

- **`Can't create testing connection via DataSource`** — БД не запущена или параметры в `profile.properties`
  не совпадают с `docker-compose.yml`. Проверьте `docker compose ps`.
- **Порт 3306 занят** (у вас уже стоит MySQL/MariaDB) — в `docker-compose.yml` замените `"3306:3306"`
  на `"3307:3306"` и в `profile.properties` укажите порт `3307`.
- **Порт 8080 занят** — `mvn jetty:run -Djetty.http.port=8090`.
- **Нет новой таблицы/поля, хотя они есть в `schema.sql`** — файл выполняется только на пустой базе,
  выполните нужный SQL вручную (см. «Как менять схему БД»).
- **Изменили `profile.properties`, а подключение не поменялось** — параметры подставляются при сборке,
  выполните `mvn clean` и запустите заново.

## Задачи

Перед началом ознакомьтесь с исходным кодом проекта, обратите внимание на аннотацию `@Json`
и её обработку в `FrontServlet`: метод страницы с `@Json` отвечает не HTML-шаблоном, а JSON-ом
(`RedirectException` превращается в `{"redirect": "..."}`, `ValidationException` — в `{"error": "..."}`).

Полезные материалы:

- SQL: [документация MariaDB](https://mariadb.com/kb/en/sql-statements/),
  [туториалы DigitalOcean](https://www.digitalocean.com/community/tags/sql);
- JavaScript и jQuery: [JavaScript Basics](https://webref.ru/dev/jqfundamentals/javascript-basics),
  [Современный JavaScript](https://learn.javascript.ru/), [jQuery](https://jquery.com/),
  [jQuery Tutorial](https://www.w3schools.com/jquery/default.asp).

Типы и ограничения полей во всех новых таблицах продумайте сами — на сдаче нужно уметь их объяснить.

### Задача 1. Регистрация: подтверждение пароля и email

- Добавьте на форму регистрации поле `passwordConfirmation`, валидируйте совпадение пароля
  и подтверждения, выводите соответствующую ошибку.
- Добавьте в сущность `User` уникальное поле `email`: измените таблицу в БД
  (и `sql/schema.sql`), обновите репозиторий и сервис.
- При регистрации валидируйте email: обязателен, уникален, содержит ровно один символ `@`
  (можно, но не обязательно, реализовать более полные правила валидации).
- Итоговая форма регистрации: `login`, `email`, `password`, `passwordConfirmation`.
- Форма регистрации отправляется через **AJAX**: ошибки выводятся под формой без перезагрузки,
  при успехе — переход на главную.
- Создайте в `js/app.js` собственную функцию `ajax` — обёртку над `$.ajax` с общим кодом
  для ваших запросов: удобные значения по умолчанию (`type: "POST"`, `dataType: "json"` и т.п.)
  и автоматическое перенаправление (`location.href = ...`), если в ответе есть `redirect`.
  Используйте её во всех AJAX-запросах этого задания — убедитесь, что кода стало меньше и он чище.

### Задача 2. Вход по логину или email, события входа и выхода

- Измените логику входа: в одно поле можно ввести как логин, так и email.
  Переименуйте поле и параметр `login` в `loginOrEmail`.
- Форма входа отправляется через **AJAX** (с помощью вашей функции `ajax`).
- Создайте сущность `Event`: `id`, `userId` (внешний ключ на `User`), `type` (`ENTER` / `LOGOUT`),
  `creationTime`. Внешний ключ можно добавить так:

  ```sql
  ALTER TABLE `Event`
  ADD CONSTRAINT `fk_Event_userId`
  FOREIGN KEY (`userId`) REFERENCES `User` (`id`);
  ```
- Создайте класс `Event` в пакете `domain`, `EventRepository` с методом `save`
  и сохраняйте событие при каждом успешном входе и выходе пользователя.

### Задача 3. Базовый класс страниц и счётчик пользователей в футере

- Выведите в футере каждой страницы общее количество пользователей: методы `findCount`
  в `UserRepository` / `UserService`, в макросе страницы — `${userCount}`.
- Чтобы не передавать счётчик в `view` в каждой странице вручную, создайте базовый класс
  всех страниц `Page` с методами
  `void before(HttpServletRequest request, Map<String, Object> view)` и
  `void after(HttpServletRequest request, Map<String, Object> view)`,
  которые потомки могут переопределять.
- В `FrontServlet` добавьте вызов `before()` / `after()` до и после выполнения action соответственно.
- В `Page#before` (или `after`) кладите в `view` значение `userCount` — теперь оно будет в футере везде.
- Перенесите в `Page#before` из `FrontServlet` установку текущего пользователя `user`,
  а из `IndexPage` — вывод `message`.
- Добавьте в `Page` метод `setMessage`, который кладёт сообщение в сессию, и вынесите туда же
  остальную работу с сессией (`request` можно сохранить в поле `Page` во время `before`).
- Можно добавить в `Page` пустой метод `action`, чтобы не писать его в каждой странице.

### Задача 4. Система сообщений

- Создайте сущность `Talk`: `id`, `sourceUserId`, `targetUserId`, `text`, `creationTime`.
- Создайте страницу `/talks`, доступную только вошедшим пользователям
  (иначе — перенаправление на главную). На ней:
  - форма отправки сообщения: `<select>` с пользователями и `<textarea>`;
  - список всех сообщений, где текущий пользователь — автор или адресат, отсортированный
    по времени создания (как в мессенджерах). Можно оформить обычной datatable:
    `id`, от кого, кому, текст, когда.
- **!** Подумайте, как отображать логины отправителей и получателей. Не попадает ли ваш подход
  под **проблему N+1** (отдельный запрос к БД на каждое сообщение)? Постарайтесь её избежать.

### Задача 5. Статьи

- Создайте сущность `Article`: `id`, `userId`, `title`, `text`, `creationTime`;
  `ArticleRepository`, `ArticleRepositoryImpl`, `ArticleService`.
- Добавьте страницу `/article` с формой создания статьи на **AJAX**: `title` (`<input type="text">`),
  `text` (`<textarea>`), кнопка `Create`. Ссылка на страницу в меню — только для вошедших пользователей.
- На главной странице выводите все статьи в обратном хронологическом порядке:
  - статьи подгружаются асинхронно через AJAX;
  - шаблон статьи задаётся элементом `<template>`;
  - если у вас есть разметка статьи из ДЗ 2 — используйте её и стили;
  - выводите логин автора, а не его id. **!** Снова помним про проблему N+1.

### Задача 6. Скрытие и показ статей

- Добавьте в `Article` поле `hidden`. На главной показывайте только нескрытые статьи.
- Создайте страницу `/myArticles` с таблицей своих статей в хронологическом порядке:
  колонки `id`, `title` и колонка с кнопкой `Hide` / `Show`.
  Сама таблица выводится **без AJAX** — обычным шаблоном.
- По нажатию кнопки отправляйте AJAX-запрос на изменение `hidden`; при успехе обновляйте
  текст кнопки и её действие, без перезагрузки страницы.
- Новое значение флага передавайте явно, а не делайте на сервере `hidden = !hidden`.
- На сервере проверяйте, что запрос пришёл от автора статьи.

### Задача 7. Администраторы

- Добавьте пользователю булево поле `admin` (по умолчанию `false`). Первого администратора
  назначьте прямо в БД: `UPDATE User SET admin = TRUE WHERE login = '...'`.
- На странице `/users` для администраторов добавьте колонку **Admin**: текущее значение `admin`
  пользователя и кнопка `Enable` / `Disable` в зависимости от него.
- По нажатию кнопки отправляйте AJAX-запрос с `id` пользователя и новым значением флага
  (передавайте его явно, а не `flag = !flag`). При успехе обновляйте отображение
  (`false` ↔ `true`, `Enable` ↔ `Disable`) без перезагрузки страницы.
- Изменять флаг могут только администраторы — проверяйте это на сервере
  (по актуальным данным из БД, а не только по объекту `User` в сессии).

**Бонус 2 (HARD, много баллов). Миграции.** Напишите собственный механизм миграций БД для проекта
(на чистом SQL или на Java) и примените его вместо ручного выполнения SQL. Как минимум:

миграций, каждая миграция применяется ровно один раз (обычно для этого заводят отдельную таблицу

Уметь объяснить преимущества такого подхода.

**Бонус 3. Роли и права (RBAC).** Вместо булева флага `admin` реализуйте простую ролевую модель:
`Role` (содержит набор `Privilege`, связь many-to-many с `User`) и `Privilege` (одно конкретное право,
например редактирование статей; связь many-to-many с `Role`). Продумайте таблицы, создайте набор
ролей и прав, назначьте их пользователям и продемонстрируйте работу.
Пример: [Baeldung — Roles and Privileges](https://www.baeldung.com/role-and-privilege-for-spring-security-registration).

## Требования ко всем задачам

- Только `PreparedStatement` с параметрами, никакой конкатенации пользовательского ввода в SQL.
- Валидация — на сервере (в сервисах); проверки в JS допустимы только как дополнение.
- Пароли в БД хранятся только в виде хеша, как в исходном коде.
- Пользовательский текст на страницах выводится экранированным (в JS — через `.text()`, не `.html()`).
